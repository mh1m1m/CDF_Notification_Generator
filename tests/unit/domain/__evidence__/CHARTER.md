## 0. Ground rules (apply to every file written under `notifications/v13/`)
1. **Evidence untouched.** Nothing under `notifications/generator/`, `journeys/`, `templates/`, `exports/`, `review/`, the registers, or the uploads is modified. V13 work lives only under `notifications/v13/` (shared folder, network mount: re-read before editing a shared file, keep edits small, read back ~10 s after writing) and the session scratch area.
2. **Synthetic only.** `@example.test`, `CDF-DEMO-2026-…`, Employee Alpha / Investigator Beta / Witness Gamma. No real person, address, credential or case. The owner is "the owner" (never a first name) in every artefact.
3. **Labels.** Every statement is FACT (read from a source or reproduced by execution), INFERENCE, PROPOSAL or UNVERIFIED. BUILT ≠ APPROVED. PROPOSED ≠ IMPLEMENTED. A mock is labelled `PRODUCTION_SUBSTITUTION_REQUIRED`. No production-readiness claim.
4. **No invented governance.** Where no approved source exists, the rule is `SOURCE_REQUIRED` and the code fails closed. No new approvals, signatures or committees are introduced without naming the reason and the authority that must grant them. Owner decisions are implemented as given; items the owner already decided are never re-asked (only their missing document may be listed).
5. **Truth before presentation.** The certainty of any display never exceeds the certainty of its authoritative source. An unrecorded event is never shown as completed. Expected steps never carry the completed symbol.
6. **Disclosure before rendering.** Every renderer receives a model that already passed the disclosure projection (`_disclosure_applied === true`); a renderer that receives anything else throws.
7. **Minimum sufficient architecture.** Seven logical domains, one Node package, no framework, no new service, no duplicate authoritative store. Platform capabilities are reused through adapters; the adapters mirror the platform's real contracts (`notify.enqueue`, `notify.claim_email_batch`, `notify.record_email_delivery`, the audit ledger) and are mocked here.
8. **Tests are the record.** Every invariant, consistency rule, disclosure scenario, authority rule and journey test case has a test with an id; results are generated by execution into `docs/V13-14_test_results.md`; failures are recorded, never hidden.
9. **Workers never call user-facing (hearthbot) tools.** Workers report by hand-back only.

## 3. Core contracts (JSON shapes; every worker uses these names)
### 3.1 CaseRecord (Domain A)
```json
{"case_id":"uuid","internal_ref":"CDF-DEMO-2026-0001","track":"WB|IR|DR","classification":"PUBLIC|INTERNAL|RESTRICTED",
 "status":{"code":"S3.05","recorded_at":"ISO","source_event_id":"evt-…"},
 "flags":{"suspended":false,"returned":false,"cancelled":false,"reopened":false,"closed":false},
 "restrictions":{"rca_required":false},"exists":true}
```
`exists:false` (no case yet) ⇒ no master journey is rendered at all (directive §6 L1 rule 4). `status.code` is the only source of Level 1. `CASE_UNCHANGED` notifications never move it.

### 3.2 ProceduralObject (Domain B)
```json
{"object_id":"uuid","type":"REFERRAL|REPORT|ALLEGATION|PROCEDURE|INVESTIGATION|TASK|MEETING|HEARING|BALLOT|RECOMMENDATION|LEGAL_OPINION|DECISION|IMPLEMENTATION_ACTION",
 "case_id":"uuid|null","journey_id":"J-…","status":"<enum of its type, §3.4>","status_source_event_id":"evt-…",
 "steps":[{"step_id":"J-…/2/1","actual":"COMPLETED|IN_PROGRESS|PENDING|SUSPENDED|RETURNED|CANCELLED|FAILED|NOT_APPLICABLE","evidence_event_id":"evt-…|null","epistemic":"RECORDED_FACT|DERIVED_FROM_VERIFIED_FACTS|NOT_APPLICABLE"}],
 "deadlines":[{"kind":"STATEMENT_DUE","at":"ISO","basis_event_id":"evt-…","basis_rule":"SOURCE_REQUIRED|DEC-F15|…"}]}
```
A step is COMPLETED only with an `evidence_event_id` whose event type is the step's `completion_event_type` (catalogue §4). Without evidence a step is at most PENDING/IN_PROGRESS (if its trigger event exists) — never COMPLETED.

### 3.5 Epistemic classes (every displayed procedural statement carries one)
RECORDED_FACT · DERIVED_FROM_VERIFIED_FACTS · EXPECTED_PROCESS · CONDITIONAL_STEP · PROPOSED_ACTION · UNVERIFIED_INFORMATION · NOT_APPLICABLE. Safe inference (DERIVED): a step whose completion event exists is COMPLETED; the case's L1 stage from the recorded code; a deadline from a recorded basis event + a stated rule. Never inferred: completion of any step without its completion event; opening of a vote from a direction; a decision from a recommendation; delivery from an export; case closure from a notification.

### 3.6 Progress layers
Layer A **Actual Progress** states: COMPLETED ✔ (`aria`: «اكتمل — تم تسجيل الإجراء»), IN_PROGRESS ● («جارٍ»), PENDING ○ («بانتظار إجراء محدد»), SUSPENDED ⏸ («موقوف مؤقتاً»), RETURNED ↩ («أُعيد لاستكمال متطلبات»), CANCELLED ✕ («أُلغي»), FAILED ⚠ («تعذر إتمامه»), NOT_APPLICABLE — («لا ينطبق»).
Layer B **Expected Process** kinds: EXPECTED, CONDITIONAL, OPTIONAL, ALTERNATIVE, PARALLEL, SUBJECT_TO_APPROVAL — all rendered with ◇ plus a text label («خطوة متوقعة», «خطوة محتملة — بحسب …», «خطوة اختيارية», «مسار بديل», «بالتوازي», «رهن الاعتماد»), dashed outline, muted colour, never ✔/●, never the words سُجل / اكتُمل / تم. The distinction must survive without colour (symbol + label + `aria-label`).

Channels: EMAIL_SUBJECT, EMAIL_PREHEADER, EMAIL_HTML, EMAIL_TEXT, CARD, IN_APP, LINK, ATTACHMENT, METADATA, EXPORT, LOG, `*`.
Row: `{"recipient":"WITNESS","field":"l1_stage_name","channel":"*","context":"*|CASE_RESTRICTED|CASE_PUBLIC|EXTERNAL","outcome":"ALLOWED|REDACTED|GENERALIZED|SAFE_REFERENCE|PROHIBITED","basis":["directive §11","DEC-24","AMB-181","SOURCE_REQUIRED","W7 §6"],"note":"…"}`.
Resolution: most specific row wins (recipient+field+channel+context > recipient+field+channel > recipient+field > recipient+`*`); **default PROHIBITED**. `project(model, {recipient, context, channel})` returns a deep copy with each field replaced according to its outcome (REDACTED → removed; GENERALIZED → the class-safe generic text; SAFE_REFERENCE → the safe reference token) and `_disclosure_applied: true` plus `_disclosure_log` (field → outcome, basis). The same decision is reused for subject, preheader, HTML, text, card, in-app, links, metadata, export and log output.
Mandatory scenario outcomes (directive §11): WITNESS → no l1/l2/l3, no case_number, event + required action only; REPORTER → public stage names only (DEC-24: portal channel only; e-mail rows PROHIBITED until decided); REFERRING_BODY → approved referral information only (SOURCE_REQUIRED beyond the acknowledgement); RECUSED_MEMBER → no deliberations, no votes, no member names; SUBJECT → what procedural rights need (request, deadline with basis, channel) and nothing of the deliberations; RESTRICTED case → every internal field PROHIBITED unless the recipient is on the approved access list.

## 9. Notification lifecycle (`src/lifecycle/notification.js`, W-D1)
States and allowed transitions: DRAFT → VALIDATED (consistency ok, disclosure applied) → AUTHORIZATION_PENDING (if the authority model requires approval) → AUTHORIZED → QUEUED (adapter `enqueue`) → SENT (adapter claim + dispatch) → DELIVERY_CONFIRMED | DELIVERY_FAILED (adapter `record_email_delivery`); DRAFT/VALIDATED/AUTHORIZATION_PENDING/AUTHORIZED/QUEUED → CANCELLED; SENT/DELIVERY_* → CORRECTED (new version, old SUPERSEDED). Idempotency key = sha256(type_code | object id | recipient id | version | disclosure policy version); duplicate prevention by key; retry policy (max attempts, backoff, FAILED after exhaustion); event ordering by `occurred_at` then `recorded_at`; every transition appends an Event (§3.3) and an evidence record (`evidence.js`, append-only). Recipient acknowledgement is an event, never a lifecycle state.
